C.O.G.N.I.T. Public API

Production documentation for external clients (web, mobile, backend-to-backend)

Base URL {{ base_url }}

Overview

This API is client-agnostic. Any HTTP client can integrate if it follows the documented protocol for idempotency, payment tokens, and state transitions.

API Style

  • All POST requests use Content-Type: application/json.
  • Success envelope: {"success": true, "data": {...}}.
  • Error envelope: {"success": false, "error": {...}}.
  • Server returns X-Request-ID on every response.
  • Timestamps are ISO-8601 UTC.
  • Mobile clients are fully supported; API does not require browser-only primitives.

Open Contracts

  • GET /docs: detailed machine-readable contract
  • /shared/contracts/openapi.v1.json: OpenAPI source
  • /shared/contracts/error_contract.json: stable error catalog
  • /shared/contracts/postman_collection.v1.json: import-ready collection

Canonical Integration Flow

  1. POST /participants to register user.
  2. POST /consent after user accepts consent.
  3. POST /payments/create to open payment session.
  4. GET /payments/{payment_public_id}/status to refresh status/token.
  5. POST /payments/{payment_public_id}/upload-url (recommended upload path).
  6. POST /payments/{payment_public_id}/verify-upload to verify screenshot.
  7. GET /images/random then POST /submit for survey loop.

Quickstart

Minimal cURL sequence for one complete participant and payment verify cycle.

1. Register Participant

curl -X POST "{{ base_url }}/participants" \
  -H "Content-Type: application/json" \
  -H "X-Idempotency-Key: 7d3f8e28-f2f4-4af7-a4cd-3d1645f8f76c" \
  -d '{
    "username":"demo_user_01",
    "email":"demo01@example.com",
    "phone":"9876543210",
    "gender_code":"male",
    "age":25,
    "location":"Ahmedabad",
    "language_code":"en",
    "prior_experience":"beginner",
    "turnstile_token":"<token_if_enabled>"
  }'

2. Record Consent

curl -X POST "{{ base_url }}/consent" \
  -H "Content-Type: application/json" \
  -d '{"public_id":"<participant_public_id>"}'

3. Create Payment Session

curl -X POST "{{ base_url }}/payments/create" \
  -H "Content-Type: application/json" \
  -H "X-Idempotency-Key: d164e2c4-7d96-4e31-9922-1db4c00c4f80" \
  -d '{
    "public_id":"<participant_public_id>",
    "amount":1,
    "turnstile_token":"<token_if_enabled>"
  }'

4. Request Upload URL (Recommended Path)

curl -X POST "{{ base_url }}/payments/<payment_public_id>/upload-url" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <payment_token>" \
  -d '{
    "sha256":"<sha256_hex>",
    "file_extension":"jpg",
    "mime_type":"image/jpeg",
    "file_size":436521
  }'

5. Verify Upload

curl -X POST "{{ base_url }}/payments/<payment_public_id>/verify-upload" \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer <payment_token>" \
  -H "X-Idempotency-Key: 61dc25b8-bfe0-4dc0-9f9b-d7277c4cd6be" \
  -d '{
    "upload_object_key":"payments/staging/<payment_public_id>/<uuid>.jpg",
    "sha256":"<sha256_hex>",
    "file_extension":"jpg",
    "mime_type":"image/jpeg",
    "turnstile_token":"<token_if_enabled>"
  }'

Security and Abuse Controls

1. Server-Only Trust

  • Payment expiry and stage transitions are enforced only in backend state checks.
  • Client timers are UX-only and never trusted for validity decisions.
  • Payload format, image/hash consistency, and token integrity are backend-enforced.

2. Turnstile Challenge

When TURNSTILE_ENABLED=true, these endpoints require turnstile_token in request body:

  • POST /participants
  • POST /payments/create
  • POST /payments/{payment_public_id}/verify-upload
  • POST /submit

3. Payment Session Token

Upload and verify routes require a signed payment write token:

  • Preferred header: Authorization: Bearer <payment_token>
  • Fallback header: X-Payment-Token: <payment_token>
  • Token is bound to payment id, participant id, signature, session, fingerprint, nonce, and expiry.

4. Idempotency and Replay Resistance

  • Mutating routes require X-Idempotency-Key.
  • Server stores request hash and rejects conflicting replays.
  • Payment nonce is one-time and rotated on token issuance/state refresh.

5. Tracking Model

  • Survey page: stored in per-submission columns (submissions.survey_*).

Error Model

Use error.code for application logic. Messages may be localized or updated over time.

Common Errors

  • VAL_MISSING_FIELDS: Required fields missing.
  • PAR_001_0001: Participant not found.
  • PAY_001_0001: Payment not found.
  • PAY_001_0002: Payment expired.
  • PAY_001_0003: Invalid payment state.
  • PAY_001_0004: Screenshot verification failed.
  • PAY_001_0011: Verify attempt limit exceeded.
  • AUTH_001_0007: Invalid payment token.
  • BOT_001_0001: Human challenge failed.
  • RATE_001_0001: Rate limit exceeded.

Error Handling Recommendations

  • Log X-Request-ID with every failed call.
  • Retry only when error.retryable=true.
  • For payment errors (PAY_*), refresh status using GET /payments/{payment_public_id}/status.
  • For token errors (AUTH_*), request a refreshed payment token via payment status endpoint.
